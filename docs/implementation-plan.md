# Kinekt Implementation Plan

This is the execution plan for moving Kinekt from a public-beta prototype to a trustworthy, measurable,
portfolio-quality local context engine. Work is ordered by dependency and risk: safety and index correctness
come before retrieval tuning, and retrieval tuning comes before broader product claims.

## Remaining External Evidence And Release Actions

The remaining items require an external service, a separately installed GUI/client, or an intentional release
decision rather than more repository implementation:

1. **Published CI evidence:** push the branch and confirm the Python 3.11-3.14 operating-system matrix, Docker
   matrix, dependency review, and scheduled integration workflow are green.
2. **Named-client calls:** run one query and one rejected unauthorized-workspace call from Claude Desktop and
   Gemini CLI. Automated SDK and Inspector discovery already pass; Codex Docker configuration parsing is recorded.
3. **Release execution:** create an intentional version tag, inspect the generated wheel, sdist, container archive,
   CycloneDX SBOM, and GitHub provenance attestation, then separately decide whether to publish to PyPI or a
   container registry.
4. **Video evidence:** record the already-scripted two-minute demo. This is deliberately not generated by the
   implementation work.
5. **Next product study:** compare agent task success with and without Kinekt on a larger external corpus before
   introducing symbol graphs, learned rerankers, tree-sitter dependencies, or orchestration frameworks.

No benchmark claim should change without a reproducible run and a pinned evaluation artifact.

## Operating Principles

- Preserve local-first behavior and avoid mandatory cloud services.
- Treat workspace containment and index correctness as release-blocking invariants.
- Prefer explicit failure and actionable recovery over silent backend drift.
- Measure retrieval quality before and after ranking or chunking changes.
- Keep the base runtime small; optional integrations must remain isolated extras.
- Do not claim client, platform, or AI behavior without a repeatable validation artifact.

## Phase 1: Trustworthy Index Foundation

### Deliverables

- Reject or skip files and symlinks whose resolved paths leave the declared workspace.
- Prune chunks and registry records for deleted, renamed, newly ignored, or unreadable files.
- Persist an index configuration fingerprint containing vector backend, embedding backend/model/dimension,
  and chunker version.
- Rebuild safely when an ingest configuration changes; reject queries against incompatible indexes.
- Add an explicit `reindex` workflow and index-status diagnostics.
- Make backend fallback behavior observable and prevent mixed embedding dimensions.

### Acceptance Gate

- Deletion and external-symlink adversarial tests pass on Linux and Windows.
- Switching embedding/vector configuration cannot silently return an empty or partial index.
- Repeated ingestion remains deterministic and unchanged files remain skipped.

## Phase 2: Workspace Authorization And Storage Reliability

### Deliverables

- Add an MCP workspace allowlist with CLI and environment configuration.
- Validate canonical workspace roots for every MCP tool.
- Separate initialization/write connections from read-only query and diagnostic connections.
- Make `doctor` non-mutating unless an explicit repair option is requested.
- Close every SQLite connection deterministically.
- Enable foreign keys, a bounded busy timeout, and WAL where write behavior permits it.
- Add input budgets for queries, messages, session IDs, and returned context.
- Ensure git context disables optional locks and uses a timeout.

### Acceptance Gate

- Unauthorized MCP paths fail without creating files or directories.
- Read-only commands do not create `.kinekt/`.
- Concurrent storage smoke tests complete without leaked handles or indefinite locks.

## Phase 3: Reproducible Docker And Developer Environment

### Deliverables

- Build and install a wheel in a multi-stage Dockerfile rather than using an editable production install.
- Include the MCP runtime and `git` in the production image.
- Run as a non-root user with documented bind-mount ownership behavior.
- Add a dedicated Docker test target that runs the same suite as CI.
- Add Compose examples for CLI and MCP workflows.
- Add dependency locking and align local, Docker, and CI dependency resolution.

### Acceptance Gate

- Docker can run `init`, `ingest`, `query`, `git-context`, and an MCP protocol smoke test.
- The Docker test target passes without writing generated files into the host repository.
- A mounted workspace does not receive unexpected root-owned files in the documented workflow.

## Phase 4: Retrieval Evaluation And Explainability

### Deliverables

- Create versioned evaluation fixtures based on real coding questions and expected files/symbols.
- Record Recall@k, MRR, nDCG, indexing time, incremental-update time, query latency, and index size.
- Add SQLite FTS5/BM25 lexical retrieval and deterministic hybrid fusion with vector results.
- Add symbol, heading, line-range, language, and construct metadata to results.
- Introduce character/token-aware chunk limits and overlap policies.
- Add `query --explain` output with component scores and ranking reasons.
- Add optional structural parsers for prioritized languages, driven by evaluation results.

### Acceptance Gate

- The evaluation command is deterministic for local fallback mode.
- Hybrid retrieval beats the recorded baseline on agreed metrics without unacceptable latency regression.
- CI fails on material retrieval-quality regressions.

## Phase 5: Genuine Session Context

### Deliverables

- Retrieve the most recent bounded history rather than the oldest messages.
- Include relevant recent turns in query rewriting and local generation.
- Add explicit context budgets and deterministic session summaries.
- Preserve provenance between a response, the query used for retrieval, and returned chunks.
- Clarify which behavior is deterministic formatting versus model-backed generation.

### Acceptance Gate

- Multi-turn tests prove that recent user constraints affect later retrieval and responses.
- Long sessions remain bounded and do not send unbounded content to local model endpoints.

## Phase 6: Portfolio And Release Proof

### Deliverables

- Replace the outdated design PDF as the primary architecture reference with versioned Markdown architecture
  documentation and Architecture Decision Records.
- Add the tracked logo, an architecture diagram, a short terminal demo, and benchmark results to the README.
- Add a validated-client matrix backed by recorded MCP integration checks.
- Add maintainer metadata, release automation, coverage, linting, type checking, and dependency/security checks.
- Publish a sample workspace and a concise engineering case study explaining major tradeoffs.

### Acceptance Gate

- Every major README claim links to code, a test, an evaluation result, or a validation record.
- Clean wheel and container installations pass the documented five-minute quickstart.
- Release artifacts are versioned and reproducible.

## Cross-Cutting Test Matrix

Each phase must preserve:

- Python 3.11 through 3.14 compatibility.
- Windows, macOS, and Linux behavior.
- Path traversal and symlink boundary protection.
- Limit clamping and bounded output behavior.
- SQLite migration coverage from every previously released schema version.
- Clean-package and clean-container installation checks.

## Deferred Until Evidence Supports It

- LangGraph or another orchestration framework.
- Hosted sync or multi-tenant storage.
- Automated source-control writes.
- A full web UI.
- Multi-agent orchestration.

These may become valuable later, but none should displace workspace trust, retrieval measurement, or a
reproducible MCP integration path.
